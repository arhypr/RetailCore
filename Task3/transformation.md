# Трансформация RetailCore: точки изменений и целевая архитектура

> Документ описывает реалистичное промежуточное целевое состояние платформы
> на горизонте трансформации (12–18 месяцев), а не «идеальную» схему полной
> переписи.
>
> Главный принцип: **не останавливать бизнес, не трогать сразу критичный write-path
> checkout/оплаты, двигаться от менее связанных зон к более связанным, обеспечивая
> промежуточную бизнес-ценность на каждом этапе.**

---

## 1. Принципы трансформации

1. **Поэтапность с промежуточной ценностью.** Каждый этап даёт бизнесу измеримый эффект: скорость, устойчивость, прозрачность или снижение ручных операций.
2. **Безопасность критичного контура.** Checkout, платёжная оркестрация и core order create остаются в монолите на всех этапах первого горизонта.
3. **Seams вместо переписывания.** Сначала выделяются границы и контракты (события, read-модели, интеграционные шлюзы), потом — постепенный вынос.
4. **Read-before-write.** Сначала выносим чтение и наблюдаемость, потом — запись.
5. **Anti-corruption layer вокруг Oracle.** Oracle остаётся, но новые компоненты не зависят от её схемы напрямую.
6. **Обратная совместимость и откат.** Любое изменение можно отключить без остановки бизнеса.
7. **Единый источник правды постепенно.** Каноническая модель заказа и событий вводится как дополнение, а не замена существующих таблиц.

---

## 2. Точки трансформации

Для каждой точки указано: проблема, почему участок подходит для изменений, зависимости и риски.

### TP-1. Канонический поток событий заказа (Order Event Hub)

- **Проблема:** нет единой модели событий заказа; аналитика, поддержка и наблюдаемость собирают картину из разных источников; расхождения данных между подразделениями.
- **Почему подходит:** read-only относительно write-path; не влияет на checkout и оплату; даёт ценность сразу нескольким стейкхолдерам (аналитика, поддержка, эксплуатация).
- **Зависимости:** монолит (источник событий), Oracle (исторические данные), аналитика, поддержка.
- **Риски:** неполнота событий, дубли, рассинхрон с фактическим состоянием; требуется аккуратный backfill.
- **Что делаем:** вводим каноническую модель бизнес-событий заказа (OrderCreated, PromoApplied, PaymentSessionCreated, PaymentConfirmed, DeliveryReserved, StatusChanged, OrderCancelled и т.д.) и публикуем их из монолита (через outbox). Потребители — аналитика, read-модели, observability.

### TP-2. Наблюдаемость и трассировка (Observability Layer)

- **Проблема:** нет end-to-end трассировки, корреляционные ID не везде; разбор инцидента — почти ручная работа.
- **Почему подходит:** не меняет бизнес-логику; снижает стоимость эксплуатации и поддержки; помогает безопасно проводить последующие изменения.
- **Зависимости:** монолит, .NET, Python, Oracle, интеграции.
- **Риски:** низкие; основная сложность — сквозной correlation ID через legacy.
- **Что делаем:** единый correlation/trace ID, централизованный сбор логов и метрик, бизнес-метрики по заказу, алерты по критичным сценариям.

### TP-3. Стабилизация интеграционного слоя (Integration Gateway)

- **Проблема:** разнородные интеграции (REST, очереди, БД, batch), разная семантика доставки, проблемы дедупликации и идемпотентности; обмен через staging-таблицы Oracle.
- **Почему подходит:** изолирует внешние зависимости от монолита; не требует изменения core order flow; снижает скрытую связность.
- **Зависимости:** монолит, .NET-сервис, Oracle staging, внешние партнёры.
- **Риски:** средние; нельзя ломать существующие контракты; нужен параллельный режим работы.
- **Что делаем:** вводим Integration Gateway как единый фасад для внешних вызовов; унифицируем контракты и события; постепенно убираем обмен через staging-таблицы; вводим идемпотентность и дедупликацию.

### TP-4. Read-модель заказа для поддержки и операций (Order Read Model)

- **Проблема:** карточка заказа не является единым источником правды; поддержка зависит от нескольких систем и команд; история разрознена.
- **Почему подходит:** read-only; не влияет на write-path; напрямую решает боль поддержки и снижает количество внутренних касаний.
- **Зависимости:** Order Event Hub, Oracle, AdminTools, поддержка.
- **Риски:** низкие/средние; нужна аккуратная агрегация из нескольких источников.
- **Что делаем:** строим единую read-модель заказа: текущее состояние, история изменений, причины отклонений, связанные платежи и логистика. Используется поддержкой, операторами, аналитикой.

### TP-5. Пост-обработка заказа (Post-Order Processing Service)

- **Проблема:** пост-обработка (уведомления, выгрузки, часть логистических и платёжных follow-up) живёт в монолите и batch; изменения в ней затрагивают ядро.
- **Почему подходит:** не входит в критичный checkout write-path; ограниченная связность; первый безопасный шаг выноса логики из монолита.
- **Зависимости:** Order Event Hub, Integration Gateway, Oracle.
- **Риски:** средние; нужен параллельный запуск и сравнение результатов.
- **Что делаем:** выносим пост-обработку в отдельный сервис, работающий по событиям; монолит публикует события, сервис выполняет follow-up.

### TP-6. Вынос чтения промо и правил (Pricing/Promo Read Service)

- **Проблема:** правила промо и цены живут в коде, Oracle, конфигах, промо-сервисе; fallback даёт другой результат; бизнес не понимает, почему цена такая.
- **Почему подходит:** выносим только **чтение** правил и расчёт справочной цены; расчёт в checkout пока остаётся в монолите.
- **Зависимости:** монолит, Oracle, промо-сервис.
- **Риски:** средние; нельзя допустить расхождения между «справочным» и фактическим расчётом.
- **Что делаем:** сервис чтения правил и справочного расчёта; монолит продолжает считать, но результаты сравниваются; постепенно снижаем зависимость от legacy-промо в Oracle.

### TP-7. Разгрузка аналитики с операционной Oracle (Analytics Offload)

- **Проблема:** тяжёлые аналитические запросы влияют на операционную Oracle; нет канонической модели заказа для аналитики.
- **Почему подходит:** read-only; не влияет на write-path; снижает нагрузку на критичный узел.
- **Зависимости:** Order Event Hub, Order Read Model, аналитика.
- **Риски:** низкие/средние; нужна валидация эквивалентности данных.
- **Что делаем:** аналитика переводится на события и read-модель; тяжёлые выгрузки из операционной Oracle постепенно сокращаются.

### TP-8. Anti-corruption layer вокруг Oracle

- **Проблема:** новые компоненты не должны зависеть от схемы Oracle и процедур; при этом Oracle остаётся.
- **Почему подходит:** не требует замены БД; снижает связность и готовит почву для постепенного отказа.
- **Зависимости:** все новые компоненты, Oracle.
- **Риски:** низкие; основная работа — договориться о контрактах.
- **Что делаем:** вводим слой доступа к данным Oracle через явные контракты; новые сервисы не читают staging-таблицы напрямую.

### Что НЕ трогаем на первом горизонте (и почему)

- **Checkout и core order create** — критичный write-path; высокая связность; ошибки напрямую бьют по выручке.
- **Платёжная оркестрация** — финансовые последствия, синхронные внешние вызовы, требования консистентности.
- **Управление статусами (write-path)** — фрагментировано, но ручные корректировки и внешние партнёры делают безопасный вынос слишком рискованным.
- **Замена Oracle** — постепенное снижение зависимости, но не замена на первом горизонте.
- **Полная переработка логистической маршрутизации** — слишком много исключений; сначала стабилизируем интеграции.

## 3. Целевая архитектура (промежуточное состояние, 12–18 месяцев)

Целевая архитектура — **не финальная**, а реалистичное промежуточное состояние, в котором:
- критичный write-path остаётся в монолите;
- вокруг монолита появляются новые сервисы и слои;
- Oracle сохраняется, но новые компоненты не зависят от её схемы напрямую;
- появляется канонический поток событий и единая read-модель;
- интеграции унифицированы через Gateway;
- аналитика разгружена от операционной БД.

### 3.1. Что остаётся в монолите

- Checkout / Order API.
- Order Processing (создание заказа).
- Pricing & Promo Logic (фактический расчёт в checkout).
- Payment Orchestration (синхронный write-path).
- Status Management (write-path переходов).
- Delivery Routing (базовый выбор маршрута).
- Admin/Support tools (с постепенным переводом чтения на Order Read Model).

### 3.2. Что изолируется (seams)

- **Order Event Hub** — outbox-публикация событий из монолита.
- **Integration Gateway** — единый фасад внешних вызовов.
- **Data Access Layer вокруг Oracle** — anti-corruption layer для новых сервисов.

### 3.3. Что выносится первым

- **Post-Order Processing Service** — пост-обработка по событиям.
- **Pricing/Promo Read Service** — чтение правил и справочный расчёт.
- **Order Read Model** — единая модель для поддержки и операций.
- **Analytics Offload** — аналитика на событиях и read-модели.

### 3.4. Границы и почему они такие

| Граница | Что входит | Почему безопасно |
|---|---|---|
| **Core Write Boundary** | Монолит: checkout, оплата, статусы, создание заказа | Критичный контур, высокая связность, финансовые риски |
| **Event Boundary** | Outbox → Order Event Hub | Read-only относительно write-path |
| **Integration Boundary** | Integration Gateway ↔ внешние партнёры | Изолирует внешние зависимости от ядра |
| **Read Boundary** | Order Read Model, Pricing/Promo Read | Не влияет на write-path |
| **Analytics Boundary** | Аналитика на событиях и read-модели | Снимает нагрузку с операционной Oracle |
| **Data Boundary** | Anti-corruption layer вокруг Oracle | Готовит почву для постепенного отказа |

## 4. Программа этапов

### Этап 1 (0–3 мес). Наблюдаемость и канонические события
- Ввести сквозной correlation/trace ID.
- Ввести outbox-публикацию канонических событий заказа из монолита.
- Развернуть Order Event Hub.
- Начать сбор бизнес-метрик по заказу.
- **Ценность:** наблюдаемость, основа для read-моделей и аналитики.

### Этап 2 (3–6 мес). Read-модель и разгрузка аналитики
- Построить Order Read Model для поддержки и операций.
- Перевести часть аналитики на события и read-модель.
- Сократить тяжёлые выгрузки из операционной Oracle.
- **Ценность:** единая карточка заказа, снижение нагрузки на Oracle, меньше ручных касаний.

### Этап 3 (6–9 мес). Integration Gateway
- Ввести единый фасад внешних вызовов.
- Унифицировать контракты и события интеграций.
- Постепенно убрать обмен через staging-таблицы.
- Ввести идемпотентность и дедупликацию.
- **Ценность:** меньше скрытой связности, стабильнее интеграции.

### Этап 4 (9–12 мес). Пост-обработка и чтение промо
- Вынести Post-Order Processing Service.
- Запустить Pricing/Promo Read Service в параллельном режиме.
- Постепенно снижать зависимость от legacy-промо в Oracle.
- **Ценность:** первый безопасный вынос логики из монолита; прозрачность цены.

### Этап 5 (12–18 мес). Anti-corruption layer и подготовка к следующим шагам
- Ввести слой доступа к Oracle для новых сервисов.
- Зафиксировать каноническую модель заказа и событий.
- Подготовить почву для постепенного снижения зависимости от Oracle.
- **Ценность:** управляемая траектория дальнейших изменений.

---

## 5. Явные ограничения и запреты

- **Не трогаем на первом горизонте:** checkout, платёжная оркестрация, core order create, write-path статусов, замена Oracle.
- **Не делаем big-bang миграцию.**
- **Не вводим новые слои оркестрации, которые усложняют систему.**
- **Не придумываем количественные NFR:** RTO/RPO, SLA/SLO, p95/p99, RPS/TPS, latency, деградация, консистентность — уточняются у стейкхолдеров.
- **Не допускаем потери прозрачности состояния заказа на переходе.**

---

## 6. Ожидаемые результаты трансформации

- Стабильнее и предсказуемее базовый order flow.
- Быстрее запускаются типовые коммерческие изменения.
- Единая картина данных по заказам и статусам.
- Меньше ручных и «героических» процессов между командами.
- Понятная платформа для следующих шагов: персонализация, партнёрские сценарии, новые каналы.
- Постепенное снижение зависимости от Oracle и зарубежных компонентов без остановки бизнеса.
