# Roadmap миграции RetailCore

> Поэтапный план перехода от AS-IS к промежуточному TO-BE (12–18 месяцев).
> Опирается на 2 (AS-IS) и 3 (TO-BE). Главный принцип — не останавливать
> бизнес, не трогать критичный write-path, давать промежуточную ценность на каждом этапе.

---

## 1. Принципы миграции

1. **Поэтапность с промежуточной ценностью.** Каждый этап даёт измеримый бизнес-эффект.
2. **Read-before-write.** Сначала чтение и наблюдаемость, потом запись.
3. **Shadow / dual-run.** Новый контур сначала работает параллельно, результаты сравниваются.
4. **Обратная совместимость и откат.** Любое изменение можно отключить без остановки бизнеса.
5. **Seams вместо переписывания.** Сначала границы и контракты, потом вынос.
6. **Anti-corruption вокруг Oracle.** Oracle сохраняется, новые компоненты не зависят от её схемы.
7. **Критичный write-path не трогаем на первом горизонте.**

---

## 2. Этапы миграции

### Этап 0. Подготовка (0–1 мес)

- **Цель:** подготовить почву, зафиксировать NFR и владельцев.
- **Объём:** уточнение RTO/RPO, SLA/SLO, p95/p99, RPS/TPS, правил деградации, консистентности ( 1, G-01…G-16); согласование владельцев доменов.
- **Промежуточное состояние:** AS-IS подтверждён, пробелы закрыты или явно приняты как риск.
- **Зависимости:** бизнес-спонсор, техлид, инфраструктура, безопасность, поддержка.
- **Риски:** незакрытые NFR → невозможность оценить этапы. Митигация: явно зафиксировать принятые допущения.
- **Критерии завершения:** согласованный список NFR и владельцев; подтверждённый план этапов.

### Этап 1. Наблюдаемость и канонические события (1–3 мес)

- **Цель:** получить end-to-end наблюдаемость и канонический поток событий заказа.
- **Объём:** correlation/trace ID, outbox-публикация событий из монолита, Order Event Hub, бизнес-метрики по заказу, алерты по критичным сценариям.
- **Промежуточное состояние:** события публикуются в shadow-режиме; потребители — только observability и аналитика.
- **Зависимости:** монолит, Oracle, эксплуатация, аналитика.
- **Риски:** неполнота событий, дубли, рассинхрон. Митигация: shadow-режим, сверка с фактическим состоянием заказа.
- **Критерии завершения:** 100% критичных сценариев покрыты событиями; correlation ID сквозной; метрики и алерты в проде.

### Этап 2. Read-модель и разгрузка аналитики (3–6 мес)

- **Цель:** единая карточка заказа для поддержки и снижение нагрузки на операционную Oracle.
- **Объём:** Order Read Model, перевод части аналитики на события и read-модель, сокращение тяжёлых выгрузок из операционной Oracle.
- **Промежуточное состояние:** поддержка работает в dual-mode (старые инструменты + read-модель); аналитика частично на событиях.
- **Зависимости:** Этап 1 (Event Hub), поддержка, аналитика, Oracle.
- **Риски:** расхождение read-модели и фактического состояния. Митигация: ежедневная сверка, поэтапный перевод.
- **Критерии завершения:** read-модель покрывает ключевые сценарии; поддержка подтверждает эквивалентность; нагрузка на Oracle снижена.

### Этап 3. Integration Gateway (6–9 мес)

- **Цель:** унифицировать интеграции, убрать обмен через staging-таблицы, ввести идемпотентность.
- **Объём:** единый фасад внешних вызовов, унификация контрактов и событий, постепенный отказ от staging, дедупликация и идемпотентность.
- **Промежуточное состояние:** часть партнёров работает через Gateway, часть — по-старому; параллельный режим.
- **Зависимости:** Этап 1 (события), монолит, .NET, Oracle, партнёры.
- **Риски:** слом существующих контрактов, дубли, задержки. Митигация: параллельный режим, canary по партнёрам.
- **Критерии завершения:** ключевые партнёры через Gateway; staging-обмен сокращён; идемпотентность подтверждена.

### Этап 4. Пост-обработка и чтение промо (9–12 мес)

- **Цель:** первый безопасный вынос логики из монолита; прозрачность цены.
- **Объём:** Post-Order Processing Service (по событиям), Pricing/Promo Read Service (параллельный режим), снижение зависимости от legacy-промо в Oracle.
- **Промежуточное состояние:** пост-обработка в dual-run (монолит + сервис); промо-чтение в shadow.
- **Зависимости:** Этапы 1–3, монолит, Oracle, промо-сервис.
- **Риски:** расхождение результатов пост-обработки и расчёта цены. Митигация: сравнение результатов, canary, откат.
- **Критерии завершения:** пост-обработка вынесена и стабильна; промо-чтение даёт эквивалентный результат; legacy-промо в Oracle не используется как основной источник.

### Этап 5. Anti-corruption layer и подготовка к следующим шагам (12–18 мес)

- **Цель:** зафиксировать границы и подготовить почву для постепенного отказа от Oracle.
- **Объём:** Data Access Layer вокруг Oracle, каноническая модель заказа и событий, подготовка к следующим этапам (логистика, платежи).
- **Промежуточное состояние:** новые сервисы работают через DAL; Oracle сохраняется.
- **Зависимости:** Этапы 1–4, техлид, инфраструктура.
- **Риски:** низкие; основная работа — договорённости о контрактах.
- **Критерии завершения:** DAL внедрён; каноническая модель зафиксирована; план следующих этапов согласован.

---

## 3. Промежуточные состояния (сводка)

| Этап | Что уже в новом контуре | Что ещё в старом | Режим работы |
|---|---|---|---|
| 1 | Observability, Event Hub | Весь write-path | Shadow |
| 2 | Read Model, часть аналитики | Write-path, часть аналитики | Dual-mode |
| 3 | Integration Gateway (часть партнёров) | Часть партнёров по-старому | Canary + dual |
| 4 | Post-Order, Promo Read | Монолит (write-path, checkout) | Dual-run |
| 5 | DAL, каноническая модель | Oracle, монолит | Постепенный переход |

---

## 4. Сквозные зависимости и риски

- **Зависимости:** Event Hub → Read Model → Analytics → Gateway → Post-Order → DAL.
- **Ключевые риски:**
  - Расхождение данных между старым и новым контуром.
  - Потеря прозрачности на переходе.
  - Скрытые зависимости при выносе из монолита.
  - Сопротивление команд.
  - Нехватка capacity on-prem.
- **Митигации:** shadow/dual-run, canary, откат, ежедневные сверки, явные критерии завершения.

---

## 5. Критерии завершения этапов (общие)

- Бизнес подтверждает эффект (скорость, устойчивость, прозрачность, снижение ручных операций).
- Технические метрики соответствуют NFR (где зафиксированы) или принятым допущениям.
- Наблюдаемость покрывает новый контур.
- Откат проверен.
- Документация и знания переданы командам.

---

## 6. Что НЕ делаем на первом горизонте

- Не трогаем checkout, платёжную оркестрацию, core order create, write-path статусов.
- Не делаем big-bang миграцию.
- Не заменяем Oracle.
- Не вводим новые слои оркестрации, усложняющие систему.
- Не придумываем количественные NFR — уточняем у стейкхолдеров.
