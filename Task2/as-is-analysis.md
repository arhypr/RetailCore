# AS-IS анализ платформы RetailCore

> Артефакт фиксирует фактическое состояние RetailCore: контекст, проблемные зоны, зависимости и ограничения для изменений.

---

## 1. Контекст системы

RetailCore — исторически сложившаяся платформа, развивавшаяся шаг за шагом под конкретные задачи бизнеса. Сегодня она критична для выручки и операций, но её развитие ограничено высокой связностью и накопленным техдолгом.

**Основные участники:**
- **Клиенты** — сайт, мобильные каналы, маркетплейсы.
- **Операторы поддержки** — разбор обращений, ручные корректировки.
- **Бизнес-пользователи** — отчёты, управление.
- **Внешние партнёры** — маркетплейсы, платёжные провайдеры, службы доставки.

**Внутренние компоненты:**
- **Java-монолит** — центральный оркестратор: checkout, обработка заказа, цена/промо, статусы, платёжная оркестрация, маршрутизация доставки.
- **Oracle** — операционная БД + бизнес-логика (пакеты, процедуры) + интеграционный слой (staging/shared tables).
- **Вспомогательные сервисы** — .NET (партнёрские интеграции), Python (аналитика).
- **Async/batch-слой** — очереди, задания, выгрузки.
- **Admin/Support tools** — ручные проверки и корректировки статусов.

**Ключевые потоки:**
- Клиент → каналы → Checkout/Order API → Processing → оплата/доставка.
- Внешние партнёры ↔ монолит (синхронно и через БД).
- Монолит ↔ Oracle (данные, логика, staging).
- Oracle ↔ аналитика (прямые SQL, витрины).
- Поддержка ↔ AdminTools ↔ статусы/Oracle (ручные действия).

## 2. Проблемные зоны

| Зона | Проявление |
|---|---|
| **Смешение ответственности в монолите** | Цена, промо, статусы, логистика, платежи переплетены в одном коде; исторические ветвления по каналам и регионам. |
| **Размытые границы доменов** | Логика распределена между кодом, Oracle, конфигами, batch-процедурами и админ-таблицами. |
| **Фрагментация статусов** | Переходы в разных модулях и batch; специальные статусы для отдельных партнёров; ручные корректировки. |
| **Ручные вмешательства** | Поддержка и операторы меняют технические статусы, инициируют повторную обработку, разбирают исключения вручную. |
| **Обмен через общие таблицы Oracle** | staging/shared tables для .NET-интеграции; скрытая связность, риск побочных эффектов. |
| **Смесь sync/async без единой модели** | Разная семантика доставки сообщений, дедупликация «на честном слове», проблемы идемпотентности. |
| **Отсутствие единого интеграционного контура** | REST, очереди, обмен через БД, batch — у каждого партнёра своё. |
| **Fallback с неполной эквивалентностью** | При недоступности промо-сервиса вызывается legacy-логика в Oracle с другим результатом. |
| **Аналитика на операционной БД** | Тяжёлые отчёты в пиковые окна влияют на производительность операционного контура. |
| **Нет канонической модели заказа** | Разные витрины дают разные цифры по выручке, отменам, промо. |
| **Слабая наблюдаемость** | Нет end-to-end трассировки, корреляционные ID есть не везде; разбор инцидента — почти ручная работа. |
| **Неоднородность каналов** | Сайт, мобильные, маркетплейсы проходят разные ветки; «одинаковый заказ» на деле разный. |
| **Зависимость от Oracle** | Пакеты, процедуры, staging-таблицы; половина фактической логики живёт в БД. |
| **Нет единого источника правды по заказу** | Карточка заказа неполная, история разрознена по системам. |
| **Дубли и проблемы идемпотентности** | Повторные отправки партнёрам приводят к дублям заявок и ручному разбору. |

## 3. Ключевые зависимости

- **Java-монолит** — центральный оркестратор; даже вынесенные сервисы часто вызываются через него.
- **Oracle** — не только БД, но и слой логики и интеграций; критическая зависимость для любых изменений.
- **Внешние партнёры** — источник задержек, дублей и исключений; правила деградации не зафиксированы.
- **Аналитика** — зависит от операционной Oracle и неоднородных источников (SQL, staging, API, batch, CSV).
- **On-prem инфраструктура** — физические серверы, ограниченная виртуализация, ресурсы близки к пределу.
- **Знания у людей** — часть логики не задокументирована; критичные сценарии держатся на опыте сотрудников.

## 4. Анализ артефактов

### 4.1. PlantUML AS-IS
Даёт верхнеуровневое представление, но не отражает: фрагментацию статусов, ручные вмешательства, Oracle как слой логики, проблемы аналитики, fallback-механизмы. Используется как отправная точка, а не эталон.

### 4.2. Фрагмент кода `OrderProcessingService.java`
Подтверждает:
- смешение ответственности в одном методе (цена, промо, доставка, статусы, SQL, внешние вызовы);
- исторические ветвления (`MARKETPLACE`, `FAR_EAST`);
- fallback на legacy-промо в Oracle;
- прямую запись в staging `INT_ORDER_EXPORT` для .NET;
- ручной разбор (`WAITING_MANUAL_REVIEW`);
- синхронные вызовы логистики и платежей в рамках оформления;
- обновление состояния через прямой SQL.

### 4.3. Интервью 1 — Техлид монолита
- Монолит — центральный оркестратор.
- Самая сложная часть — оформление и пост-обработка заказа.
- Несколько механизмов расчёта цены; правила в коде, Oracle, конфигах, промо-сервисе.
- Статусы фрагментированы, есть ручные вмешательства.
- Интеграции в ядре в основном синхронные; есть async и обмен через БД.
- Узкие места: Oracle и длинные транзакции, тяжёлые SQL.
- Вынос функций затруднён скрытыми зависимостями.
- Часть критичной логики — в Oracle-процедурах и пакетах.

### 4.4. Интервью 2 — Логистика
- Нет единого интеграционного контура: REST, очереди, БД, batch.
- Правила выбора маршрута распределены по слоям; ручные настройки.
- Oracle критична: справочники, staging, технические таблицы.
- Разная семантика доставки сообщений; проблемы дедупликации.
- Самое рискованное — недооценить исключения (крупногабарит, split shipment, регионы).
- Главная проблема — отсутствие одного источника правды.

### 4.5. Интервью 3 — Аналитика
- Нет единого событийного потока; часть отчётов real-time, часть — ночная загрузка.
- Нет канонической модели заказа; конфликты цифр между подразделениями.
- Данные из разных источников: SQL, staging, API, batch, CSV.
- Аналитическая нагрузка влияет на операционную Oracle.
- Проблемы качества данных и слабый lineage.
- Главный риск — зависимость от операционной Oracle и отсутствие нормализованного потока событий.

### 4.6. Интервью 4 — Поддержка
- Карточка заказа не является единым источником правды.
- Поддержка зависит от нескольких команд и инструментов.
- Ручные и полуформализованные сценарии восстановления заказа.
- Болезненны отклонения от happy path: зависшие статусы, изменение сроков, частичные отмены, возвраты.
- Поддержка компенсирует архитектурные пробелы людьми и опытом.

### 4.7. Интервью 5 — Бизнес-заказчик
- Прежняя модель развития не даёт нужной скорости.
- Изменения дорогие, рискованные, непредсказуемые.
- Нельзя останавливать бизнес; полный редизайн — не цель.
- Критичны checkout, оплата, обещание доставки.
- Нужна единая картина данных и промежуточная ценность этапов.

## 5. Ключевые выводы

1. **Java-монолит** остаётся центральным оркестратором; радикальные изменения checkout слишком рискованны.
2. **Oracle** — критический узел: данные, логика, интеграции, staging. Отказ должен быть поэтапным.
3. **Высокая связность** и смешение ответственности затрудняют вынос функций.
4. **Статусы фрагментированы**, есть ручные корректировки; нет единой модели.
5. **Интеграции разнородны**: REST, очереди, БД, batch; разная семантика доставки.
6. **Нет единой картины данных**; аналитика зависит от операционной Oracle.
7. **Слабая наблюдаемость**: end-to-end трассировки нет, корреляционные ID не везде.
8. **Инфраструктура on-prem** близка к пределу; масштабирование требует времени.
9. **Количественные NFR отсутствуют**: RTO/RPO, SLA/SLO, p95/p99, RPS/TPS, latency, деградация, консистентность.
10. **Стратегия изменений** — поэтапная трансформация с промежуточной ценностью и откатом; начинать с менее связанных зон (интеграции, события, наблюдаемость), не трогая сразу checkout и core order create.

## 6. Ограничения для изменений

| ID | Ограничение | Зона влияния |
|---|---|---|
| L-01 | Нельзя останавливать бизнес. | Все изменения |
| L-02 | Big-bang миграция неприемлема. | Программа трансформации |
| L-03 | Высокая связность монолита и Oracle. | Вынос функций, замена БД |
| L-04 | Скрытые зависимости (таблицы, batch, админ-сценарии, старые API). | Декомпозиция |
| L-05 | Разнородные интеграции и разная семантика доставки. | Логистика, партнёры |
| L-06 | Ручные операции — часть текущего процесса. | Поддержка, операции |
| L-07 | On-prem инфраструктура и ограниченная виртуализация. | Масштабирование, capacity |
| L-08 | Аналитика на операционной Oracle. | Производительность, данные |
| L-09 | Неполная документация и знания у людей. | Все изменения |
| L-10 | Внешние партнёры вне контроля. | Интеграции, SLA |
| L-11 | Отсутствие количественных NFR. | Планирование, оценка |
| L-12 | Требуется промежуточная бизнес-ценность. | Программа этапов |

---

## 7. Итог

RetailCore — исторически сложившаяся платформа с центральным Java-монолитом, критической ролью Oracle и разнородными интеграциями. Ключевые архитектурные проблемы — высокая связность, фрагментация статусов, отсутствие единой картины данных и наблюдаемости, зависимость от Oracle и on-prem. Эти особенности определяют ограничения для изменений и требуют поэтапного, управляемого подхода к трансформации с промежуточной бизнес-ценностью и возможностью отката.
